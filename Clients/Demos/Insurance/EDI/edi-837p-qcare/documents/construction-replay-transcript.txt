What this interface does
----------------------------------------
Directory-poll X12 837P professional claims, parse with PilotFish EDI TableData (837-Q1), and map each ST to QCare's 2100-byte outpatient (OT / B837) flat-file record. Demo only — golden-path fidelity against client samples, not full WTX/ITX parity.

Who it's for
----------------------------------------
- Source: operator dropping *.txt / *.edi / *.837 into input/inbound
- Destinations: QCare text under output/qcare/; archived EDI under output/archive/; debug EDI XML under output/debug/
- Demo vs production: synthetic/client sample PHI; no SNIP gate; REPOSHDR claim numbering is a demo-stable header, not byte-identical to staged WTX
- Anyone watching the construction video or reading this transcript

2. Poll EDI 837P Files
Here's a directory listener — it watches a local folder. That folder is /opt/pilotfish/input/inbound. We're only taking .edi, .txt, .837 files. It checks about every 5 seconds. After pickup we move the file aside so the folder stays clean.

3. Fork - XPath
This XPath fork splits the file so each transaction set becomes its own message.

4. Extract Claim Identity
XPath evaluation copies a few fields off the XML onto the transaction so later steps can use them.

5. Pretty-Print EDI XML
This processor pretty-prints the XML — line breaks and indent — so the file on disk is readable.

6. Debug Write EDI XML
This writes a debug copy of the XML so we can inspect what the route saw. That lands under /opt/pilotfish/output/debug.

7. Map EDI XML To QCare Flat File
Now for the mapping — we're using the stock XSLT processor with transform-837p-to-qcare.xslt. The stylesheet writes a 2100-character fixed-width text record.

8. Write QCare Record
Then we write the file out to /opt/pilotfish/output/qcare.
