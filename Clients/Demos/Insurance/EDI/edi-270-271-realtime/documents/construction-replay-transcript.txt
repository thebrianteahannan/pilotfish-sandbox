What this interface does
----------------------------------------
Clinic (or EHR) posts once. PilotFish owns the full synchronous 270 to payer to 271 round-trip and returns clinic-ready JSON on the same HTTP request.

Who it's for
----------------------------------------
- Sources: Clinic Web UI posts EligibilityRequest XML to PilotFish /eip/rest/eligibility/check
- Destinations: mock payer X12 271; clinic JSON summary; audit files under output/
- Demo vs production: Demo only — canned AAA/EB, no SNIP, no clearinghouse
- Anyone watching the construction video or reading this transcript

[Setup]

S1. Welcome
Welcome to the PilotFish demo: EDI 270/271 Realtime Eligibility. Clinic (or EHR) posts once. PilotFish supports the whole flow out of the box.

S2. Pipeline overview
Before we wire anything, here's the flow end to end. Clinic (or EHR) posts once.

S3. External systems
And here's what sits around the routes. Mock Payer, PilotFish eiPlatform, and Demo Web UI. All of those are spun up in docker images for this demo.

[1 - Realtime Eligibility Check]

1. First route
Clinic (or EHR) posts once. Starting with a blank canvas on the first route.

2. Realtime Eligibility REST
First up is a REST listener — clinic systems POST to /eip/rest/eligibility. The resources are check. We wait for the route to finish so the caller gets an HTTP response back.

3. Snapshot Inbound Request
Next we archive a copy of the body — original name plus a timestamp. That lands under /opt/pilotfish/output/requests.

4. Conditional Router
Then a conditional router. POST to check takes the realtime round-trip; anything else is a 405.

5. Map Request To 270 EDI XML
Now for the mapping — we're using the stock XSLT processor with transform-request-to-270-edi-xml.xslt. It maps payerIdSafe, traceSafe, dateSafe.

6. Empty Error Body
Now for the mapping — we're using the stock XSLT processor with transform-method-not-allowed.xslt.

7. Pretty-Print 270 EDI XML
This processor pretty-prints the XML — line breaks and indent — so the file on disk is readable.

8. Set 405
We set the HTTP status to 405 Method Not Allowed.

9. Write 270 EDI XML
Then we write that XML to disk so we can inspect it. That lands under /opt/pilotfish/output/270.

10. 405 Headers
We set the response content type so the clinic client knows what it got back.

11. XML to EDI 270
Here's the EDI transformation — it turns our EDI XML into X12 text on the wire.

12. Method Not Allowed
This transport replies on the original REST call with whatever body we just built.

13. Write 270 EDI Wire
Then we write the X12 text to disk. That lands under /opt/pilotfish/output/270.

14. Post 270 To Payer
Then we HTTP POST the 270 to the payer at http://mock-payer:8210/x12/270. After the response comes back, post-processors keep going on that same transaction.

15. Snapshot Raw 271
Then we write the X12 text to disk. That lands under /opt/pilotfish/output/271.

16. Save Raw 271
We keep the raw 271 on the transaction so we can wrap it without losing the wire text.

17. Wrap 271 For Parse XSLT
We wrap the raw 271 in a tiny XML envelope so the parse stylesheet can read it.

18. Load Wrapped 271 Body
Then we put that wrapped XML back on the body so the next XSLT can parse it.

19. Map 271 Wire To JSON
Now for the mapping — we're using the stock XSLT processor with transform-271-xml-to-json.xslt. Watch the for-each over ebSegs. It maps memberId, last, first.

20. Write JSON Summary
Then we write the JSON summary to disk. That lands under /opt/pilotfish/output/responses.

21. Set 200 Check
We set the HTTP status to 200 OK.

22. JSON Response Headers
We set the response content type so the clinic client knows what it got back.

23. Return Summary To Clinic
This processor replies on the original REST call, so the clinic gets the JSON on the same request.

[Closing]

C1. Demo complete
That's the demo — clinic (or EHR) posts once. Thanks for choosing PilotFish.
